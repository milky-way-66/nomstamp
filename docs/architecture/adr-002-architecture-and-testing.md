# ADR-002 — Clean architecture, design patterns and the test strategy

**Date:** 2026-08-19 · **Status:** proposed
**Drivers:** maintainability, test-driven development, everything covered by automated tests
at unit / integration / e2e levels.

---

## 1. The problem with the code written so far

| Current | Why it blocks TDD |
|---|---|
| Views use `@Query` and `modelContext` directly | Business rules can only be exercised by launching a simulator |
| `PhotoStore.shared` singleton | Global mutable state; no way to substitute a fake in a test |
| `Meal(eatenAt: Date())` reads the clock inline | "A meal logged today sorts above yesterday's" is untestable |
| Dedupe rules live in a static enum touching `ModelContext` | Cannot test the rule without a database |
| `AppleMapsPlaceSearch` constructed at the point of use | Every search test would hit Apple's live servers |

The *logic* is fine. The *placement* is wrong. This ADR moves it.

---

## 2. Layers

Dependencies point **inward only**. Nothing in Domain imports SwiftUI, SwiftData, MapKit or UIKit.

```
┌─────────────────────────────────────────────────────────┐
│  App  — composition root: builds the object graph        │
│  ┌───────────────────────────────────────────────────┐   │
│  │ Presentation — SwiftUI views + @Observable models  │   │
│  │  ┌─────────────────────────────────────────────┐  │   │
│  │  │ Domain — entities, use cases, port protocols │  │   │
│  │  │          pure Swift, zero Apple frameworks   │  │   │
│  │  └─────────────────────────────────────────────┘  │   │
│  │ Data — SwiftData / FileManager / MapKit adapters  │   │
│  └───────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘
        Presentation → Domain ← Data      (Domain depends on nothing)
```

**Domain** owns `Place`, `Meal`, `Photo` as plain `struct`s, the use cases, and the *ports*
(protocols) it needs the outside world to satisfy. It is the only layer where business rules live.

**Data** implements those ports: SwiftData for persistence, `FileManager` for photo bytes,
MapKit for place search. Persistence models are separate `@Model` classes with mappers.

**Presentation** holds one `@Observable` view model per screen, depending only on Domain
protocols. Views become as close to logic-free as practical.

**App** is the only place that knows every concrete type — the composition root.

### Why domain entities are separate from `@Model` classes
Making SwiftData `@Model` classes double as domain entities is less code, and it is the
pragmatic default for a small app. It is rejected here because it puts a database dependency
inside every business rule: the rule "a place with no meals is a wishlist place" would then
require a `ModelContainer` to test. With plain structs, that test is three lines and runs in
microseconds. The price is mapper code, which is mechanical and itself unit-tested.

## 3. Packages — the decision that makes TDD fast

Domain and Data become **local Swift packages**, not app targets:

```
food-map/
├─ Packages/
│  ├─ FoodMapDomain/       pure Swift  → tests run on macOS, no simulator
│  └─ FoodMapData/         SwiftData + ImageIO + MapKit adapters
├─ FoodMap/                SwiftUI app + view models
├─ FoodMapUITests/         XCUITest end-to-end
└─ FoodMap.xcodeproj       generated by xcodegen
```

An iOS app-target test suite must boot a simulator — seconds per run, and painful in a
red-green-refactor loop. A pure Swift package runs `swift test` natively on macOS in well
under a second. Since the domain is the layer under test most often in TDD, this is where
the leverage is.

SwiftData, ImageIO and MapKit are all available on macOS, so most **integration** tests can
run there too. Only UIKit image encoding and the UI itself require the simulator.

## 4. Design patterns, and why each one is here

Patterns are chosen for a reason, not for the catalogue.

| Pattern | Applied to | Reason |
|---|---|---|
| **Use Case / Interactor** | `LogMealUseCase`, `SavePlaceUseCase`, `FindPlacesNearbyUseCase`, `DeleteMealUseCase` | One class per user intention, mapping 1:1 to the use cases in `use-cases.md`. Each is a single public `execute` method — trivially testable, no UI needed. |
| **Repository** | `PlaceRepositoryProtocol`, `MealRepositoryProtocol` | Domain talks about saving places, not about SwiftData. Enables an in-memory fake for tests. |
| **Port & Adapter (Hexagonal)** | `PlaceSearchPort` → `AppleMapsPlaceSearchAdapter`, `PhotoStoragePort` → `FileSystemPhotoStorage`, `LocationPort` → `CoreLocationAdapter` | Already agreed for search (ADR-001, "keep it swappable"); generalised to every external dependency. |
| **Clock abstraction** | `ClockPort` → `SystemClock` / `FixedClock` | Time is an input, not an ambient global. Makes date-ordering rules deterministic. |
| **Mapper** | `PlaceMapper`, `MealMapper` | Converts persistence models ↔ domain entities, both directions unit-tested. |
| **MVVM** | one `@Observable` model per screen | SwiftUI's natural fit; keeps views declarative and logic assertable without rendering. |
| **Composition Root / DI** | `AppDependencies` | All wiring in one file. No service locator, no singletons — dependencies are constructor-injected. |
| **Result + typed errors** | use case returns | Failures are values the view model must handle, not crashes. |

Deliberately **not** used: no Coordinator router (SwiftUI `NavigationStack` already does this),
no generic `AnyRepository` abstraction over everything, no reactive framework beyond
Observation. Each would add indirection this app has no need for.

## 5. Test strategy

Framework: **Swift Testing** (`@Test`, `#expect`) for unit and integration, **XCUITest** for e2e.

### 5.1 Unit tests — Domain, run on macOS, milliseconds
Every use case against in-memory fakes. Examples that must exist:

- a place with zero meals is a wishlist place; adding a meal makes it visited (UC-6)
- logging a meal at an existing place does not create a second place (UC-4 / 3a)
- saving a place whose provider id already exists returns the existing one
- a place with no provider id, same name, 30 m away → duplicate; 300 m away → not
- meals for a place come back newest-first (UC-3)
- with location denied, `LogMealUseCase` still succeeds given a manual coordinate (UC-1 / E1)
- Near Me returns only places inside the radius, sorted ascending by distance (UC-5)
- Near Me with nothing in range returns empty rather than an error (UC-5 / 2a)
- clustering: two places 10 m apart collapse at city zoom, separate at street zoom
- a single-place cluster keeps the exact coordinate, never an average

### 5.2 Integration tests — Data adapters against the real thing
- SwiftData repository against an **in-memory `ModelContainer`**: round-trip a place with
  meals and photos; cascade delete removes children.
- `FileSystemPhotoStorage` against a **temp directory**: save → read back → delete, and
  deleting a place removes the files from disk, not just the rows.
- EXIF reader against **fixture JPEGs** committed to the repo, including a southern/western
  hemisphere image to prove the sign handling, and one with no GPS at all.
- `AppleMapsPlaceSearchAdapter` — network-dependent, therefore **tagged and excluded from
  the default run**. Keeps the suite deterministic and offline-safe while still allowing a
  deliberate check that Vietnam search still behaves (the ADR-001 measurements, as a test).

### 5.3 End-to-end — XCUITest on the simulator
The app is launched with `-UITestMode` so the composition root swaps in an in-memory store
and a **stubbed search adapter with fixed Vietnamese fixtures**. This is what makes e2e
deterministic: no live Apple Maps, no real GPS, no camera.

The camera does not exist in the simulator, so `PhotoStoragePort` is fed from a bundled
fixture image in test mode. Journeys to cover:

1. Empty state → add a meal from a fixture photo → pin appears on the map.
2. Save a place by name → wishlist pin appears → open it, note is shown.
3. Wishlist place → "I ate here" → log a meal → pin becomes visited, note survives (UC-6).
4. Two meals at one restaurant → exactly one pin, badged "2".
5. Near Me in a seeded city → saved place listed with distance; in an empty city → the
   explicit "nothing saved near here" message.

### 5.4 What gets measured
Coverage is reported but not chased as a number. The rule instead: **every use case in
`use-cases.md`, including its alternate and exception flows, has at least one named test.**
Traceability from story → use case → test is the point.

## 6. TDD working agreement
1. Pick one use case flow from `use-cases.md`.
2. Write the failing domain test naming that flow (`test_logMeal_withLocationDenied_...`).
3. Minimum code to pass.
4. Refactor with the test green.
5. Only once the domain is green, wire the adapter and the screen.

Domain-first means the interesting decisions are made and proven before any pixel exists.

---

## 7. Consequences
- **More files and more indirection.** For an app this size that is a real cost, paid
  deliberately in exchange for a fast test loop and a swappable map provider.
- **Mapper boilerplate** between persistence and domain.
- **`@Query` is given up** in views; view models load through repositories instead, which
  means refresh after mutation becomes explicit rather than automatic.
- **The code written so far gets refactored, not discarded** — models, clustering, EXIF
  parsing and the search adapter all move into their new layers largely intact.
